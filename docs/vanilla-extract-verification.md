# Vanilla-extract distribution verification

Run from the repository root after installing development dependencies:

```sh
node scripts/build-vanilla-extract.mjs
node scripts/vanilla-extract-consumers.mjs build all
node scripts/verify-vanilla-extract.mjs
node --test test/vanilla-extract.test.mjs
```

`artifacts/vanilla-extract/verification.json` is the measured result, not an estimate. Rerun after package or consumer changes. Build outputs and evidence are generated locally; this workflow does not publish or push anything.

## What the distribution check proves

1. `npm pack --ignore-scripts` produces a real tarball containing compiled JS, CSS, types, metadata, and notices, not `.css.ts` authoring sources.
2. The tarball installs offline in a new temporary project. This project has no vanilla-extract packages, runtime dependencies, or peer dependencies.
3. A fresh Node process imports the package by its public package name with no `window` or `document`. Exported classes, themes, and CSS-variable references are ordinary strings.
4. An isolated TypeScript consumer resolves the packed declarations with both Bundler and NodeNext resolution, without `skipLibCheck` or installed vanilla-extract types.
5. A production Vite build imports the public JS and `styles.css` exports using no Vite plugins and no project config. Compiled output is saved under `artifacts/vanilla-extract/plain-consumer/`.

Vanilla-extract remains a development dependency of the authoring repository. “No runtime/plugin dependency” describes downstream consumption of the compiled style package, not authoring `.css.ts` files.

## Supported framework scope

The [current Destyler UI README](https://github.com/destyler/ui#pick-your-framework) lists React, Vue, Solid, and Svelte. This verification uses all four published `@destyler-ui/*` packages, pinned at `0.0.1-beta.21`; it does not substitute lower-level core adapters. Exact installed versions are recorded in `verification.json`. This covers the current four UI frameworks, not every framework supported by lower-level Destyler core.

## SSR and hydration

`test/vanilla-extract-ssr.mjs` runs each framework and styling variant in fresh Node processes. The SSR process has no DOM shim. It renders real `@destyler-ui/react`, `@destyler-ui/vue`, `@destyler-ui/solid`, and `@destyler-ui/svelte` Switch and Dialog primitives, including labels, controls, hidden input, trigger, backdrop, positioner, content, title, description, and close trigger.

Solid and Svelte fixtures are compiled separately for server and browser with their normal framework plugins, without any vanilla-extract plugin. Solid uses its official `generateHydrationScript()` bootstrap. No browser globals are present when the server bundle imports or renders.

A separate hydration process loads that saved HTML into happy-dom, hydrates with the same primitive tree, toggles the Switch, opens and closes the Dialog, and reopens it. The original server-rendered Switch control and Dialog trigger must retain object identity after hydration, preventing an unnoticed full client rerender from counting as a pass. Console errors and warnings are recorded. React recoverable hydration errors are captured explicitly. The styled version imports the installed tarball's JS, not authoring source. The unstyled version uses the same primitives with no style classes, providing a control for primitive or harness failures.

There are 16 cases: four frameworks × styled/unstyled × server/hydration. This is SSR/hydration evidence for inline, initially closed dialogs with explicit stable IDs. It is not universal proof about all Destyler components or framework SSR frameworks. Portals, initially open dialogs, visual layout, focus trapping, keyboard behavior, nested themes, and portal theme inheritance require separate browser checks. The CSS itself is separately verified through bundling; happy-dom is not used to claim visual CSS parity.

## Reading the size results

- `stylePackage` reports actual compiled CSS, class/token-map JS, their concatenated byte size, and the npm tarball. Gzip uses level 9. Concatenated gzip is informational; real HTTP transfers usually compress JS and CSS separately.
- `tailwindSwitchDialogBaseline`, when generated by the consumer workflow, records a component-scoped baseline using the existing Switch/Dialog/button/label recipes. This is the meaningful component-scope comparison.
- `fullDemoBuildContextOnly` lists existing full-demo assets separately. These include unrelated components and application code, and must not be presented as an equivalent Switch/Dialog baseline.
- `consumerBuildsContextOnly` includes React/Vue runtime, primitive behavior, and application code. Do not compare these totals directly to the standalone style package.

Even the component-scoped Tailwind baseline is not guaranteed byte-for-byte feature equivalence: the existing recipes include additional variants and animation helpers. Shared preflight/theme overhead must be identified. Size alone does not establish behavioral or visual equivalence or justify a production migration.

## Regression tests

`test/vanilla-extract.test.mjs` checks the private package guard, no runtime/peer dependencies, CSS side-effect declaration, public stylesheet export, compiled class/token contracts, and state/reduced-motion CSS. Built-output assertions skip if the package has not been built; the full verification script requires a built package and fails rather than silently skipping.

The verification found and helped fix one real distribution issue: an emitted `index.d.ts` re-export of `./styles.css` passed Bundler resolution but failed NodeNext. The build now flattens declarations into `index.d.ts`; both consumer modes are checked to prevent regression.
